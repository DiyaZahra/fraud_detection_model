# PaySim Mobile Money Fraud Detection

An end to end machine learning project that detects fraudulent mobile money transactions in the PaySim dataset, from exploratory analysis and feature engineering to model comparison, error analysis and a deployed web app.

Live app: [[LIVE APP LINK]](https://frauddetectionmodel1.streamlit.app/)


---

## Overview

Mobile money platforms process millions of transactions every day, and only a tiny fraction of them are fraudulent. Reviewing each one by hand is not possible, so a model has to act as the first line of defence. This project builds that model and serves it through a simple web interface where a user can enter transaction details and get a fraud probability.

The main challenge is class imbalance. Fraud makes up about 0.13 percent of the data, so a model that labels everything as normal would still reach 99.87 percent accuracy while catching no fraud at all. For that reason the project is evaluated with Precision, Recall, F1 and PR-AUC instead of accuracy.

## Results

Evaluated on a held out test set of 1,272,524 transactions that contains 1,643 fraud cases. The test set keeps the original class imbalance.

| Model | Precision | Recall | F1 | False alarms | Missed fraud |
|---|---|---|---|---|---|
| Logistic Regression | 0.9715 | 0.9976 | 0.9844 | 48 | 4 |
| Random Forest | 0.9988 | 0.9976 | 0.9982 | 2 | 4 |
| XGBoost | 0.9964 | 0.9976 | 0.9970 | 6 | 4 |

Random Forest reached a PR-AUC of 0.9987 and was selected as the final model. It produced the fewest false alarms and also gave the smallest model file, at roughly 0.22 MB.

An important detail is that all three models missed the same four fraud cases. This points to a limit in the data and not a weakness in a single model, which is explained in the error analysis section below.

## Dataset

| Property | Value |
|---|---|
| Source | PaySim on Kaggle, `ealaxi/paysim1` |
| Rows | 6,362,620 |
| Columns | 11 |
| Time span | 744 steps, where one step is one hour, so 30 days |
| Fraud rate | About 0.13 percent, roughly 8,213 transactions |
| Fraud occurs in | TRANSFER and CASH_OUT only |

PaySim is a synthetic dataset generated by a simulator that is based on real mobile money logs. It contains no real customer information.

## Key Findings From Exploratory Analysis

- Fraud appears only in TRANSFER and CASH_OUT transactions, so the other three types carry no fraud signal.
- In 97.82 percent of fraud cases the amount equals the full balance of the sender, which means the account was emptied. This happens in 0.00 percent of normal transactions and is by far the strongest signal in the data.
- The old and new balance columns are almost perfectly correlated, 1.00 for the sender and 0.98 for the receiver.
- Amounts and balances are heavily skewed, with a few very large values and many small ones. Tree based models handle this without any transformation.
- The `isFlaggedFraud` column from the original rule based system is set for only about 16 rows, so it was dropped.

## Feature Engineering

Five features were created from the raw columns.

| Feature | Definition | Purpose |
|---|---|---|
| `errorBalanceOrig` | `newbalanceOrig + amount - oldbalanceOrg` | Checks whether the sender balance changes consistently with the amount |
| `errorBalanceDest` | `oldbalanceDest + amount - newbalanceDest` | Same check for the receiver |
| `drainedAll` | 1 if `amount == oldbalanceOrg`, otherwise 0 | Captures the account emptying pattern |
| `hour` | `step % 24` | Hour of day |
| `destMerchant` | 1 if the receiver ID starts with M, otherwise 0 | Separates merchants from customers |

Transaction type was one hot encoded. The ID columns, `isFlaggedFraud` and `step` were dropped. The final model uses 15 features in this order.

```
amount, oldbalanceOrg, newbalanceOrig, oldbalanceDest, newbalanceDest,
hour, errorBalanceOrig, errorBalanceDest, drainedAll, destMerchant,
type_CASH_IN, type_CASH_OUT, type_DEBIT, type_PAYMENT, type_TRANSFER
```

In the feature importance plots of both tree models, `drainedAll` and `errorBalanceOrig` ranked at the top, while `hour` contributed little.

## Handling Class Imbalance

- The train and test split is stratified, so both parts keep the same fraud ratio.
- Logistic Regression and Random Forest use `class_weight='balanced'`.
- XGBoost uses `scale_pos_weight` of about 773.75, the ratio of normal to fraud rows in the training data.
- Resampling methods such as SMOTE were not used, and the test set was never balanced, so the reported scores reflect real conditions.

## Models

| Model | Notes |
|---|---|
| Logistic Regression | Baseline model, used with `StandardScaler` in a pipeline |
| Random Forest | 50 trees, maximum depth 12, final model |
| XGBoost | 300 estimators, depth 6, learning rate 0.1, histogram tree method |

The data was split 80 to 20 with `random_state=42`.

## Error Analysis

All three models missed the same four fraud transactions. Three of the four have a sender balance of zero before the transaction, and one has an amount larger than the sender balance, so none of them follow the account emptying pattern.

The more useful finding is that only 25 fraud cases look like this, while 1,308,541 normal transactions look the same. A model that flagged them would block a very large number of genuine customers to catch a handful of fraud cases. Missing these four is therefore a reasonable trade off, and catching them would likely need extra information such as customer history, which this dataset does not provide.

## Web App

The Streamlit app lets a user enter the transaction type, amount, balances and receiver type. It calculates the engineered features with the same formulas used in training, builds the 15 feature input in the correct order and returns the fraud probability from the Random Forest model.

To run it locally

```bash
git clone [[REPOSITORY LINK]](https://github.com/DiyaZahra/fraud_detection_model)
cd fraud_detection_model
pip install -r requirements.txt
streamlit run app.py
```

## Limitations

- The data is synthetic, so the very high scores should not be expected on real transaction data. Real fraud is more varied and changes over time.
- The fraud pattern in the simulation is simple, and the model mostly learns one dominant rule.
- A random split was used. A time based split would be closer to real deployment.
- The `newbalanceOrig` and `newbalanceDest` columns are only known after a transaction completes, which makes real time use harder.
- Only a single train and test split was evaluated, with no cross validation, and hyperparameters were set by hand.
- The default decision threshold was used without tuning.
- The app checks one transaction at a time and is intended as a demonstration, not for real financial decisions.

## Future Work

- Tune the decision threshold using the precision recall curve
- Add stratified cross validation and hyperparameter search
- Use a time based train and test split
- Add SHAP explanations for individual predictions
- Create customer history features such as past transaction counts and averages
- Support batch prediction through CSV upload in the app
